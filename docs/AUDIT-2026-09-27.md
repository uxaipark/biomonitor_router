### 전체 평가

설계 자체는 좋다. 와이어 파서는 길이·경계 검사가 빈틈없고, 저장 포맷(항목 CRC → 블록 봉인 → 봉인된 것만 백업 → 원격 재읽기 SHA 검증 → 검증된 것만 삭제)과 권한 모델(경로별 `requirement()`, 테넌트 스코프, 역할 위계 cap, 파라미터 바인딩 SQL, 256비트 세션 토큰의 sha256 저장)은 운영을 의식해 짜여 있다. 잠금을 `.await` 너머로 들고 가는 곳도 없고, XSS 싱크도 없다.

구조적 약점은 네 가지로 모인다.

1. **시간의 출처를 구분하지 않는다.** 게이트웨이가 보낸 `hdr.ts_ms`를 그대로 알람 생존 판정·저장 블록 키·prune·백업 나이에 쓴다. 게이트웨이 시계가 5초만 느려도 그 게이트웨이 환자들의 바이탈 알람이 조용히 전부 꺼지고, 재접속 후 재생(replay)이 이미 봉인된 블록을 파괴할 수 있다.
2. **"개발 모드" 하나에 운영 안전이 걸려 있는데 기본값이 켜짐이다.** 시드 비밀번호가 README에 있고 `/api/auth/test-accounts`가 인증 없이 그 비밀번호를 내려 준다. 첫 로그인 비밀번호 변경은 서버가 강제하지 않는다.
3. **PHI 마스킹은 API 응답 계층에서만 동작한다.** 병원 IT(phi=0)가 의사 계정을 만들거나, 분석 서버 주소·백업 대상을 자기 호스트로 바꾸거나, curl 설정에 개행을 넣으면 우회된다.
4. **실행 경로에 감독자가 없다.** `setsid nohup` 런처 + `panic = "abort"` + 1초 대기 재시작 스크립트라서 패닉 한 번이면 사람이 알아챌 때까지 전면 정지다. 이미 준비된 systemd 유닛(`deploy/pi/`)이 설치되어 있지 않다.

## 1. 서버 핵심 파이프라인 (ingest · wire · state · registry · gateways · alarms · metrics · output · grouping · control · main · sysmon)

- **[critical] ingest.rs:42 — `listener.accept().await?` 한 번 실패하면 수신 리스너 전체가 조용히 죽는다**
  - 문제: accept 루프가 `?`로 에러를 반환하고 main.rs:69의 `tokio::spawn`은 JoinHandle을 버린다. 로그도 재시작도 없다. `EMFILE`/`ENFILE`/`ECONNABORTED`/`ENOBUFS` 같은 일시 오류가 그대로 Err로 온다.
  - 시나리오: fd가 많이 잡힌 상태에서 게이트웨이 2,200대 동시 재접속 → `EMFILE` 한 번 → 이후 어떤 게이트웨이도 접속 못 함(기존 연결은 유지). 로그에 아무것도 없다.
  - 제안: 오류는 `warn!` 후 100 ms sleep하고 `continue`; 치명 오류(EBADF)만 종료. main에서 JoinHandle을 감시해 종료 시 이벤트를 남긴다.
  - 확신도: CONFIRMED

## 2. 저장·백업 (patch_store · backup)

전제: 기본 `ROUTER_STORE_GZIP=1`(config.rs:53). 아래 첫 두 항목은 gzip ≥ 1일 때 성립한다(런처·배포 env는 0으로 덮으므로 현재 RP5 운영에서는 비활성이나, README 기본 설치는 1).

- **[critical] patch_store.rs:330-342 (+82-100) — 늦게 온 레코드가 이미 gzip 봉인된 블록을 통째로 덮어쓴다**
  - 문제: `seal_file()`은 `<key>.rec.gz`가 있어도 `fs::rename`으로 무조건 덮어쓴다. `file_writer`는 `.rec.gz`로 바뀐 키에 Append가 오면 새 빈 `.rec`를 옆에 만든다. 이 작은 `.rec`가 Close되면 봉인기가 원본 `.rec.gz`를 늦은 레코드 몇 개짜리로 교체한다. 이어서 backup은 크기가 바뀐 파일을 다시 올려 원격 사본까지 덮어쓴다(backup.rs:1783-1795).
  - 시나리오: 게이트웨이 재접속 후 저장분 재생 → 2시간 전 `hdr.ts_ms` → 봉인된 키 → 2시간치 파형이 로컬·원격 모두 소실.
  - 제안: 대상 `.rec.gz`가 있으면 rename 금지(`.late-<ms>.rec`로 별도 보관), writer는 봉인된 키에 append하지 않음, 백업은 로컬이 작아지면 덮어쓰지 않음.
  - 확신도: CONFIRMED (경로) / 트리거 빈도 PLAUSIBLE

- **[high] patch_store.rs:342 vs 92-111 — 봉인기가 `.rec`를 unlink하는 동안 writer가 같은 파일에 append 핸들을 열 수 있다.** 이후 append는 전부 unlink된 inode로 가서 조용히 사라진다(STORE_BYTES는 증가). 두 스레드 사이에 동기화가 없다. CONFIRMED
- **[high] backup.rs:1649 (+602) — `tombs` HashMap이 런타임에 무한 증가, `backup_catalog`도 영구 증가.** 상한 도달 후 ≈3만 항목/일 → 연 1천만. RSS와 SD 카드 sqlite 모두. 제안: `tombs.retain(14d)`, 카탈로그 보존 기간. CONFIRMED
- **[high] backup.rs:551-573,641 / patch_store.rs:970 — 삭제 보호가 fail-open.** `router.db` 열기 실패 → in-memory DB → "대상 없음" → ACTIVE=false → 백업 안 된 블록 삭제. 마지막 대상을 지우는 것만으로도 즉시 보호가 풀린다. 제안: 로드 실패 시 ACTIVE 강제 true, 마지막 대상 삭제에 유예 시간. CONFIRMED
- **[high] patch_store.rs:682-700 + admin_api.rs:755-761 — overview가 구간 상한 없이 모든 ECG 샘플을 메모리에 올린다.** 하루 ≈86 MB, 30일이면 GB. `hist_sem`도 안 잡는다. 제안: 스트리밍 집계 + 7일 상한. CONFIRMED
- **[high] patch_store.rs:812 / ingest.rs:263 — 게이트웨이 `hdr.ts_ms`를 검증 없이 블록 키로.** 미래 시각 블록은 영영 봉인·백업이 안 되고, 재생과 실시간이 섞이면 키가 번갈아 바뀌어 Close마다 블록 전체 재gzip. CONFIRMED
- **[medium] main.rs:112-118 — graceful shutdown이 writer 완료 전에 종료될 수 있다.** (1절과 동일) CONFIRMED
- **[medium] patch_store.rs:950,969-998 — prune이 `.restore-cache` 파일을 저장소 파일로 취급.** blocked 집계 부풀림, 비상 삭제 시 거짓 incident, STORE_BYTES 오차. CONFIRMED
- **[medium] patch_store.rs:460-463,633-635 — 항목 하나가 깨지면 그 뒤의 블록 전체를 못 읽는다(resync 없음).** ENOSPC 부분 쓰기 후 이어 붙이면 이후 전부 유실인데 `bad=1`로만 집계. 제안: 항목 길이 프리픽스(에뮬레이터 store.py·verify.py 동기 필요) 또는 헤더 탐색 resync. CONFIRMED
