# 패치 재고 기능 검토 (2026-10-01)

실무 기준: 의료기기 공급사 VMI(공급사가 병원 재고를 대신 관리)·위탁(쓴 만큼 청구) 절차 — 근거 `inventory-vmi-practice.md`.

## 검토에서 나온 문제 (실사용 기록 근거)
| 문제 | 실제 증상 | 조치 |
|---|---|---|
| 상자·개수 혼동 | 발주 2,220상자(=22,200개) 작성됨 | 발주 창에 '= N개' 환산, 권장의 3배 넘으면 경고 |
| 발주가 '작성'에서 멈춤 | 작성 4건이 진행 안 됨 | 작성 단계 없앰: 요청 → 병원 승인 → 출고 → 수령, 카드마다 다음 할 일 버튼 |
| 누가 승인·수령하는지 없음 | 아무나 모든 단계 | 공급사(리셀러·영업)=요청·출고·계약·이동, 병원(IT·간호·원무)=승인·수령, 서버에서 강제 |
| 기록 밖 사용이 묻힘 | 재고 0 상태에서 233개 부착 → 메모만 | 카드에 '기록보다 많이 사용' 경고 → 방문 점검으로 해소 |
| 로트 입력이 자유 문자 | 로트 '1', '2' | GS1 바코드 스캔(로트·유효기간 자동), 출고 때 로트를 지정하고 수령은 확인만 |
| 실사가 총수량만 | 로트별 차이·만료 처리 불가 | 방문 점검: 로트별 센 수량, 폐기·반품, 발견 재고, 병원 확인자 필수, 점검 주기 알림 |
| 계약 개념 없음 | 위탁/구매, 병원 단가 없음 | 계약·보충 설정: 운영 방식, 병원 단가, 약정 수량, 계약 종료일 |
| 청구 근거 없음 | — | 월 사용 명세(위탁=사용 수량, 구매=입고 수량) 인쇄 |
| 유효기간 임박분 처리 없음 | — | 병원 간 이동(같은 로트·유효기간, 품절 빠른 병원 우선 제안) |
| 리콜 대응 없음 | — | 로트 추적: 병원별 남은 수량·입고 이력 |
| 통계 용어 노출 | σ, z, 리드타임, 서비스수준 | 배송 기간(주문→병동), 재고 확인 주기, 방문 점검 주기, 품절 방지 수준(보통/권장/높음) |
| 목표에 조금 모자라도 발주 권고 | 재고 충분한데 1상자 발주 | (s,S) 규칙: 남은 재고+오는 중 ≤ 발주 시점일 때만 |

## 절차 (화면 흐름)
1. 계약·보충 설정(공급사) — 한 번.
2. 첫 입고 등록 — 지금 병원에 있는 재고를 로트별로(스캔).
3. 사용 — 이 라우터 병원은 패치 부착마다 자동 차감(유효기간 빠른 로트부터).
4. 발주 — 카드가 '○/○까지 발주'를 띄우면 요청 → 병원이 발주번호로 승인 → 공급사가 로트 스캔해 출고 → 병원이 받은 수량 확인(차이 기록). 자동 발주 요청을 켜면 1단계가 자동.
5. 방문 점검 — 점검 주기마다 로트별로 세고 병원 확인자 이름을 남긴다. 만료분은 폐기·반품, 임박분은 이동.
6. 월 사용 명세 — 청구 근거 인쇄(공급사·병원 확인란).

## 남은 일 (다음 단계 후보)
- 병원 안 보관 장소(병동·외래) 단위 재고 — 지금은 병원 단위.
- 점검·명세 확인서의 전자 서명, 이메일 발송.
- 포괄 발주번호(blanket PO: 한도·잔액·만료).
- 반품(RMA) 번호와 공급사 창고 입고 처리 — 지금은 병원 쪽 차감만.
- 유효기간 기반 목표 재고 상한(남은 유효기간 안에 다 못 쓰는 양은 보내지 않기).
- 공급사·리셀러 창고 재고(트렁크 재고) 위치.
- 오프라인 스캔 대기열(지하 창고 등 통신 불가 장소).
- 다른 병원 라우터와의 재고 동기화: 지금은 이 라우터 DB 가 포털 역할. 실제 운영은 중앙(클라우드) 재고 DB 로 옮겨야 여러 병원 라우터가 함께 쓴다.
